## Detailed Findings

### F1. CRITICAL — Bottle download fails on GHCR redirect

**File**: `src/bottle/mod.rs:80-92`

The bottle download creates a `reqwest::Client` with `redirect::Policy::none()` to prevent token leakage on HTTPS→HTTP downgrades. However, GHCR blob endpoints (`/v2/.../blobs/sha256:...`) always issue a 307 redirect to Azure/S3 CDN storage. With redirects disabled, `response.status()` is 307, `is_success()` returns false, and the download bails with "bottle download failed (HTTP 307)".

This is likely a functional blocker — no bottles can be downloaded.

**Fix**: Use `Policy::custom()` that follows redirects only to HTTPS URLs:
```rust
let policy = reqwest::redirect::Policy::custom(|attempt| {
    if attempt.url().scheme() == "https" {
        attempt.follow()
    } else {
        attempt.error(anyhow::anyhow!("refusing HTTP redirect"))
    }
});
```

### F2. CRITICAL — Unbounded memory allocation without Content-Length

**Files**: `src/bottle/mod.rs:94-105`, `src/cask/mod.rs:155-163`

`MAX_DOWNLOAD_SIZE` is only checked against `response.content_length()`. If the server uses chunked transfer encoding (no Content-Length header), the check is silently skipped and `response.bytes().await?` buffers the entire response into memory with no limit.

**Fix**: Stream the response body with a running byte counter:
```rust
let mut bytes = Vec::new();
let mut stream = response.bytes_stream();
while let Some(chunk) = stream.try_next().await? {
    bytes.extend_from_slice(&chunk);
    if bytes.len() as u64 > MAX_DOWNLOAD_SIZE {
        anyhow::bail!("download exceeds size limit");
    }
}
```

### F3. CRITICAL — No CI/CD pipeline

No `.github/workflows/` directory exists. The project has no automated build, test, clippy, rustfmt, or security audit on push/PR. This is a hard blocker for open-source release.

**Fix**: Create `.github/workflows/ci.yml` with: build (3 targets), `cargo test`, `cargo clippy -- -D warnings`, `cargo fmt --check`. Create a release workflow for binary publishing.

### F4. HIGH — Daemon stop has PID validation issues

**File**: `src/cli/mod.rs:1196-1204`

1. `pid_str.trim().parse::<i32>()` accepts negative numbers. `kill(-N, SIGTERM)` sends SIGTERM to the entire process group N.
2. No TOCTOU protection — the daemon may have died and the PID reused by another process between read and kill.

**Fix**: Validate `pid > 0`. Better: try to acquire the PID file lock first (using existing `is_running()` / `PidGuard` mechanism). If the lock is free, the daemon isn't running — report that and clean up the stale PID file.

---

### F5. HIGH — Cask ZIP extraction has no path traversal protection

**File**: `src/cask/mod.rs:267-306`

`install_from_zip` delegates to the external `unzip` command without path validation on extracted contents. Unlike the bottle tar extraction (which has `reject_unsafe_path` + canonical parent checks), ZIP extraction is unguarded. A malicious ZIP could write outside the temp directory.

**Fix**: Use `-d` with a dedicated sandbox directory and validate extracted paths afterward, or use a Rust ZIP library with the same `reject_unsafe_path` checks.

---

### F6. HIGH — Cask app name not validated for path traversal

**File**: `src/cask/mod.rs:241-257`, `src/cli/mod.rs:884`

App names from the API are used directly in `appdir.join(app_name)` where `appdir` is `/Applications`. A compromised API could return `../../etc/malicious.app`.

**Fix**: Validate that `app_name` contains no `/` or `..` components.

**Fix**: Run `cargo fmt` and commit.

### F8. HIGH — Tests don't exercise production code

`den` is a binary crate (`[[bin]]`), so integration tests in `tests/` cannot import internal modules. Two of five test files (`bottle_test.rs`, `manifest_test.rs`) replicate production logic instead of testing it. 21 of 34 tests (62%) test replicated code — if production code drifts, tests still pass.

**Fix**: Add `[lib]` alongside `[[bin]]` in Cargo.toml so tests can `use den::bottle`, `use den::manifest`, etc. Then rewrite tests to call production functions.

---

### F9. HIGH — Service module is macOS-only without cfg guard

**File**: `src/service/mod.rs` (all)

`launchctl`, `~/Library/LaunchAgents/`, and plist handling are macOS-only. Will fail at runtime on Linux. Similarly, `src/daemon/mod.rs` generates a launchd plist unconditionally.

**Fix**: Gate behind `#[cfg(target_os = "macos")]`. On Linux, use systemd or skip with a clear error.

---

### F10. HIGH — set_key stores numbers as strings when existing value is null

**File**: `src/settings/mod.rs:130-158`

When an `Option<u64>` field (e.g., `daemon.interval_secs`) has never been set, the JSON value is `Null`. The match arm `Null | String(_)` treats numeric input like `"3600"` as a string `"3600"`. This produces `{"interval_secs": "3600"}` which fails `serde_json::from_value::<Option<u64>>` deserialization.

**Fix**: When existing value is `Null`, try `parse::<u64>()` → Number, then `parse::<bool>()` → Bool, then fall back to String.

### F12. MEDIUM — Non-atomic file writes
