## Architecture

den is a universal package/environment manager (C++23, CMake+Ninja) that consumes the Homebrew ecosystem. Everything compiles into one static lib (`den_lib`) linked by the `den` binary (`src/main.cpp` → `den::Cli::run`) and the `den_tests` runner.

- **Entry / dispatch.** `src/main.cpp` is a 3-line shim into the CLI. `src/cli/cli.cpp` (~1600 LOC) is a CLI11-based parser/dispatcher for install/uninstall/upgrade/use/env/search/info/deps/outdated/doctor/daemon/migrate/selfupdate/tap/set. `src/core/config.cpp` reads HOME, DEN_HOME, HOMEBREW_PREFIX/CELLAR/CASKROOM from the environment; the store is the shared `/opt/homebrew/Cellar`.
- **Provider seam** (`src/provider/`). `PackageProvider` interface (install/uninstall/list/package_root/binary_paths); `registry.cpp` selects a provider. `homebrew_provider.cpp` is the default fallback (SAT solver, T42/T64 trust cross-check, bottle download+extract+relocate). python/go/node/cargo providers shell out via `exec.cpp` (`posix_spawnp`, explicit argv, no shell).
- **Download / trust** (`src/download/`, `src/trust/`). `http.cpp` fetch_url (libcurl, 500MB cap). `fetch.cpp` is a content-addressed cache keyed by sha256, verifying hash before caching; `fetch_ghcr_blob` does anonymous GHCR token + blob pull. `archive.cpp` extracts via libarchive with an `is_path_unsafe()` guard and `ARCHIVE_EXTRACT_SECURE_NODOTDOT` — but deliberately **not** SECURE_SYMLINKS. `trust_model.cpp` performs the two-source hash cross-check (Homebrew API vs den replica on raw.githubusercontent.com).
- **Store / env** (`src/store/`, `src/env/`). `store.cpp` (Cellar layout, canonical containment). `link.cpp` (`is_valid_package_name`, symlink trees). `environment.cpp` `materialise()`. `manifest.cpp` (`env_slug()`, manifest.json read/write).
- **Build-from-source** (`src/build/`). `source_build.cpp` fetches formula `.rb`, runs bundled Portable Ruby or falls back to a native parser + generic build detection, executing build commands via `std::system`/`popen` with `shell_quote`. `relocate.cpp` does Mach-O/ELF prefix rewriting.
- **Background** (`src/daemon/`, `src/supervisor/`). Background staging of upgrades; launchd service management; `selfupdate.cpp` pulls the latest GitHub release, checksum-verifies, and atomically renames over itself.
- **Index** (`src/index/`): metadata, SAT solver, dep resolution. Plus doctor/migrate/tap/smoke/activity/settings. Tests via ctest.

## Invariants

The audit tracked twelve stated invariants. The confirmed findings each violate one or more:

1. **Extraction containment** — all filesystem writes confined to dest. `is_path_unsafe()` rejects absolute/`..` pathnames and hardlinks, but SECURE_SYMLINKS is disabled and symlink targets are never checked. **[VIOLATED — Finding 2]**
2. **Hash-before-admit** — every downloaded artifact must SHA256-match before entering cache/store. (Holds; integrity check is present but is orthogonal to content sanitisation.)
3. **Two-source trust cross-check fails closed** — install proceeds only on agree (Proceed) or single-source-reachable (WarnProceed). (Holds at the cross-check level.)
4. **Malformed replica fails closed at parse** — `parse_replica_document` throws on bad digests. (Holds at parse level.)
5. **self-update verifies before atomic replace.** **[VIOLATED — Finding 4:** verification is skipped when no checksum asset exists.**]**
6. **Names crossing into paths/shell are validated** by `is_valid_package_name`/`valid_pypi_name` before use. **[VIOLATED — Finding 1:** source-build path reaches a shell before validation.**]**
7. **Multi-version coinstall** — installing never removes an existing version; `use` atomically switches. (Not contradicted, but see Finding 5's collateral relinking.)
8. **which_package containment** resolves symlinks and confirms real path under store root. (Holds.)
9. **unlink_tree removes only links into the target package.** (Flagged as a path-boundary risk; not among the confirmed set.)
10. **env_slug is a single-component slug** that cannot expand into a parent dir; separators percent-encoded. **[VIOLATED — Finding 3:** `.` is not encoded, so `..` survives.**]**
11. **Shared Cellar co-ownership** — den deletes only what it manages. (Holds.)
12. **Manifest writes crash-safe/atomic.** **[VIOLATED in spirit — Finding 5:** atomic write cannot protect against a *read* that silently empties a corrupt manifest, converting recoverable corruption into permanent state loss.**]**

## Trust boundaries

1. **Bottle/source archive contents** from GHCR/CDN — untrusted bytes extracted via libarchive. Entry names, hardlinks **and symlink targets** plus data written through them are attacker-influenced; SECURE_SYMLINKS disabled. → **Finding 2**.
2. Bottle hash metadata from formulae.brew.sh — one of two roots of trust.
3. den replica snapshot `known_hashes.json` — second root of trust; fail-closed digest validation.
4. **Homebrew formula Ruby source** — parsed into build commands via `std::system`/`popen`; `shell_quote` guards env values but the `brew info … + name` fallback concatenates the name into a shell command. → **Finding 1**.
5. **GitHub Releases + browser_download_url for self-update** — supplies binary and checksum from the same origin; if the release lacks a `.sha256` asset, verification is skipped (fail-open). → **Finding 4**.
6. GHCR anonymous token + OCI blob endpoint — blob hash-verified afterward.
7. Environment variables (HOME/DEN_HOME/HOMEBREW_*) — control every store/cache path.
8. **User CLI arguments** — package names, versions, env paths flow into store paths, symlink creation, `env_slug`, and provider argv; validation must gate every downstream use. → **Findings 1 and 3**.
9. Provider subprocess boundary — external toolchains whose stdout is parsed and exit codes drive control flow.
10. Background daemon / supervisor / selfupdate — act with the user's authority without interactive confirmation. → **Finding 4**.

## Findings

### F1 — Command injection via unvalidated package name in `den install -s` (brew info popen)

- **Severity:** Critical
- **Verdict:** CONFIRMED (reachability: confirmed; invariant-validity: confirmed)
- **Location:** `src/build/source_build.cpp:192` (sink); entry at `src/cli/cli.cpp` source-build branch
- **Invariant violated:** #6 (names crossing into a shell must pass `is_valid_package_name`); trust boundaries #8 (CLI args → shell) and #4 (formula-name → shell)

**Failure scenario.** `den install -s 'x; touch /tmp/pwned #'`. The source-build install branch iterates `install_names` raw and calls `den::build_from_source(cfg, idx, name, version)` without ever calling `is_valid_package_name`. When the name is not in the index, `fetch_formula_source` returns `""` (`idx.find` is null), so both Ruby build paths (guarded by `!formula_source.empty()`) are skipped and control reaches `extract_build_recipe`, whose fallback runs `run("brew info --json=v1 " + name + " 2>/dev/null")`. `run()` is `popen((cmd + " 2>&1").c_str(), "r")` — i.e. `/bin/sh -c`. The shell executes `brew info --json=v1 x; touch /tmp/pwned # 2>/dev/null 2>&1`; the `;` runs an arbitrary command and `#` comments out the trailing redirects. Any name containing `;`, `$(...)`, backticks, `|`, `&&`, spaces, etc. is executed with the user's privileges. The injected command fires unconditionally — even if `brew` is absent — before `run` returns non-zero and `extract_build_recipe` throws.

**Evidence.** Sink: `src/build/source_build.cpp:192` (`run("brew info --json=v1 " + name + …)`); `run()` popen at `src/build/source_build.cpp:29-39`. Unvalidated entry: the `-s/--build-from-source` loop in `src/cli/cli.cpp` (`for (const auto& name : install_names) … den::build_from_source(...)`), no validation. Empty-source fall-through: `src/build/source_build.cpp:147-151` (null pkg → `return ""`), Ruby paths at lines 220 & 258 skipped, line 288 → `extract_build_recipe` → line 192. Gate bypassed: `is_valid_package_name` defined `src/store/link.cpp:93-103`, only invoked at `link.cpp:107,144,178` via `materialise`, which runs **after** the vulnerable loop. A `shell_quote` helper is defined immediately below `run()` in the same file but is not applied to `name`. Precondition is only a populated index (`den update` first), the normal state.

**Fix sketch.** Call `is_valid_package_name(name)` (reject on failure) at the top of the install callback / `install_packages` / `build_from_source`, before any name reaches a store path or shell. Additionally replace the `run("brew info … " + name)` popen with an argv-based `run_tool({"brew","info","--json=v1",name})` so no shell is involved even if validation regresses.

**Verification step.** Add a test that invokes the source-build entry with `name = "x; touch $TMPDIR/pwned #"` against a populated stub index and asserts (a) `build_from_source`/install throws or returns an error before executing, and (b) no `pwned` sentinel file was created. After the fix, assert `is_valid_package_name` rejects the metacharacter name and the `brew info` invocation uses argv, not `/bin/sh -c`.

### F2 — Archive extraction escapes dest via attacker-controlled symlink target

- **Severity:** High
- **Verdict:** CONFIRMED (reachability: confirmed; invariant-validity: confirmed)
- **Location:** `src/download/archive.cpp:79` (guard); options at `:67-68`; hardlink-vs-symlink asymmetry at `:84`
- **Invariant violated:** #1 (extraction must confine all writes to dest); trust boundary #1

**Failure scenario.** A malicious/compromised bottle or source tarball (untrusted GHCR/CDN bytes) contains two entries: (1) a symlink entry whose pathname is safe (e.g. `pkg/evil`) but whose symlink *target* is `/tmp/attacker` or `../../../../etc`; (2) a regular file entry `pkg/evil/payload`. `is_path_unsafe` inspects only `archive_entry_pathname` and `archive_entry_hardlink` — it never calls `archive_entry_symlink`, and `ARCHIVE_EXTRACT_SECURE_SYMLINKS` is deliberately disabled. libarchive creates `dest/pkg/evil -> /tmp/attacker`, then writes `payload` *through* that symlink, landing the file at `/tmp/attacker/payload`, outside dest. `SECURE_NODOTDOT` does not catch this: the escape lives in the symlink target, not in a `..` pathname component, and neither the target nor the payload pathname contains `..`. Overwriting e.g. `$HOME/.zshrc` yields code execution.

**Evidence.** `src/download/archive.cpp:20-39` (`is_path_unsafe` checks pathname only); `:67-68` (write-disk options = TIME|PERM|SECURE_NODOTDOT, SECURE_SYMLINKS omitted with an explicit comment about Homebrew's internal symlinks); `:79` (pathname validated) and `:84-87` (hardlink validated) — `archive_entry_symlink` never called anywhere in the extraction path (repo-wide grep confirms absence); `:101` & `:106` rewrite only pathname and hardlink target, leaving the symlink target untouched. In libarchive's `archive_write_disk`, `check_symlinks` runs only under SECURE_SYMLINKS; O_EXCL/O_NOFOLLOW guard only the final path component, not a symlinked parent. Reached from `src/provider/homebrew_provider.cpp:117` (`extract_archive` on `fetch_ghcr_blob`/`fetch_archive` bytes verified at `:105`/`:107`), and also `source_build.cpp:321`, `portable_ruby.cpp:85`, `bundle.cpp:71`. The SHA256 + replica cross-check proves the bytes match the manifest hash but does not inspect contents — a malicious bottle simply ships bytes matching its own declared hash.

**Fix sketch.** Either enable `ARCHIVE_EXTRACT_SECURE_SYMLINKS` (Homebrew's internal `.brew/` symlinks are relative and safe under it), or add an explicit guard: for entries where `archive_entry_symlink(entry)` is non-null, reject when the target is absolute or contains a `..` component — mirroring the existing hardlink check.

**Verification step.** Build a crafted tar with a symlink `pkg/evil -> $TMPDIR/attacker` followed by a regular file `pkg/evil/payload`, run `extract_archive` into a temp dest, and assert no file appears outside dest (specifically `$TMPDIR/attacker/payload` must not exist) and extraction is rejected. Confirm the fix with both an absolute-target and a `../`-laden-target case.

### F3 — `env_slug` fails to encode `..`; path traversal out of manifests/envs (`den env remove ..` deletes den_home)

- **Severity:** High
- **Verdict:** CONFIRMED (reachability: confirmed, with empirical repro; invariant-validity: confirmed)
- **Location:** `src/env/manifest.cpp:56` (`env_slug`); callback at `src/cli/cli.cpp:917-931`; `env_dir` at `src/env/environment.cpp:27-29`
- **Invariant violated:** #10 (env_slug must be a single-component slug that cannot expand into a parent directory); trust boundary #8

**Failure scenario.** `env_slug` percent-encodes `/`, `-`, and `%` but leaves `.` untouched; its only whole-string guard is `env_path == "/"`. So `env_slug("..")` returns `".."` verbatim. `den env remove ..` special-cases only `/`, then computes `manifest_dir = den_home/manifests/env_slug("..")` = `den_home/manifests/..` (resolves to `den_home`) and `envdir = den_home/envs/..` (also `den_home`), and calls `fs::remove_all` on both — recursively deleting the entire den_home tree (all manifests, envs, cache). The `den env create /..` variant escapes too: `env_slug("/..")` strips the leading slash to `".."`, so `manifest_file` writes `den_home/manifests/../manifest.json` = `den_home/manifest.json`. env names are raw required CLI input, never passed through any validation.

**Evidence.** `src/env/manifest.cpp:56-88` (`env_slug`: encodes only `/`, `-`, `%`; special-cases only exact `"/"` → `"ROOT"`; no `.` encoding). `src/cli/cli.cpp:917-931` (`env remove`: guards only `"/"`, then `fs::remove_all` on manifest_dir and env_dir). `src/env/environment.cpp:27-29` (`env_dir` merely concatenates `env_slug`). No `is_valid_*`/canonicalize anywhere on the env-path flow (grep of `manifest.cpp` shows `manifest_file`/`env_slug`/`write_manifest` all take the raw string). **Empirical repro:** compiling and running `fs::remove_all("<home>/manifests/..")` recursively deleted all of `<home>`'s contents (sentinel `important.txt`, `envs/keep.txt`, `cache/` all gone), leaving only the emptied home dir; the final removal of the `..` component errored into an ignored `std::error_code` *after* contents were already destroyed.

**Fix sketch.** In `env_slug`, also percent-encode `.` (or at minimum reject/encode any slug equal to `.` or `..`), so no slug can act as a filesystem navigation component. Alternatively validate env names at the CLI boundary (reject names containing `..` or resolving to `.`/`..`) and canonicalize env paths before use.

**Verification step.** Add tests: `env_slug("..")` and `env_slug("/..")` must not equal `..` and must not contain a path separator or a bare `.`/`..` component. Integration: point DEN_HOME at a temp dir seeded with a sentinel manifest, run `den env remove ..`, and assert the command is rejected and the sentinel survives.

### F4 — self-update overwrites running binary without verification when the release has no `.sha256` (fail-open)

- **Severity:** High
- **Verdict:** CONFIRMED (reachability: confirmed; invariant-validity: confirmed)
- **Location:** `src/selfupdate/selfupdate.cpp:146-165` (skip); gate at `:130`; overwrite at `:200`
- **Invariant violated:** #5 (self-update must verify SHA256 before atomic replace); trust boundary #5

**Failure scenario.** `check_for_update()` sets `checksum_url` only when a release asset named `den-<ver>-<suffix>.tar.gz.sha256` exists (`:124-126`). The sole hard gate is `download_url.empty()` (`:130`); a missing checksum asset is not gated, so `UpdateInfo` is returned with `checksum_url == ""`. In `apply_update`, `if (!info.checksum_url.empty())` (`:147`) is skipped, leaving `expected_hash == ""`, and `if (!expected_hash.empty())` (`:159`) then skips hashing entirely — control falls straight through to extract (`:178`) and `fs::rename(new_binary, exe)` (`:200`), overwriting the live executable with unverified bytes. Secondary path: even with `checksum_url` set, an empty/whitespace body leaves `ss >> expected_hash` empty (`:150-151`) → same silent skip. Reached from the `self-update`/`update` CLI subcommand (`cli.cpp:1512` → `check_for_update` at `:1531` → `apply_update` at `:1536`) with no additional gating. A release published without its checksum asset (a realistic maintainer mistake) silently installs an unauthenticated binary; code executes on next invocation.

**Evidence.** `src/selfupdate/selfupdate.cpp:130` (only `download_url` gated), `:138` (`checksum_url` may be empty), `:147` (fetch skipped when empty), `:150-151` (empty on blank body), `:159` (hashing skipped when `expected_hash == ""`), `:200` (`fs::rename` over live exe). Caller: `cli.cpp:1512/1531/1536`.

**Threat-model nuance (does not change the verdict).** The tarball and its checksum come from the same GitHub release over the same HTTPS origin, so the checksum is a corruption/omission integrity check, not an independent signature — an attacker who tampers with the release can also swap the `.sha256`, and TLS already defeats a pure network MITM. The concrete, realistic trigger is therefore the **fail-open on a missing/empty checksum asset**, not a novel external-attacker capability. The defect and the invariant violation stand regardless.

**Fix sketch.** Treat a missing/empty `expected_hash` as a hard error, not a skip: after fetching, require `!expected_hash.empty()` and `is_sha256_hex(expected_hash)`, else `throw UserError("self-update refused: no verifiable checksum for release")`. Only proceed to the rename after a confirmed hash match.

**Verification step.** Add a test that drives `apply_update` with an `UpdateInfo` whose `checksum_url` is empty (and a second with a whitespace checksum body) and asserts it throws/refuses and does **not** rename over the target binary. Positive case: a matching checksum still applies.

### F5 — `read_manifest` swallows JSON parse failure; next mutating command clobbers the manifest (state loss)

- **Severity:** High
- **Verdict:** CONFIRMED (reachability: confirmed; invariant-validity: confirmed)
- **Location:** `src/env/manifest.cpp:162-167` (catch); parse at `:124`; write at `:169-203`
- **Invariant violated:** #12 (manifest writes/reads must be crash-safe against corruption; a recoverable corrupt file must not become permanent loss)

**Failure scenario.** `read_manifest` wraps the whole parse (`json j = json::parse(in)` at `:124`) in a try block; a corrupt/unparseable existing file throws `json::parse_error` (a `json::exception`), caught at `:162-164` with only `SPDLOG_WARN`, then returns the Manifest `m` unchanged from `:116` — i.e. fully empty (packages/auto_deps/origin never populated). The file-absent case is handled separately (`:118-120`), so there is **no** distinction between "absent" (legitimately empty) and "present but corrupt" — both return an empty manifest. Every mutating command is read-modify-write under flock via `with_manifest` (`manifest_impl.h:67-73`): `read_manifest` → `fn(manifest)` → unconditional `write_manifest`. So if `manifest.json` is corrupt for any reason (partial write from a crash on a legacy non-atomic path, FS corruption, a 0-byte/truncated file, a bad hand-edit), `den install X` reads an EMPTY manifest, `install_packages` (`install.cpp:24-36`) adds only X, and `write_manifest` atomically replaces the file with a manifest containing ONLY X — every previously installed package is silently dropped, and the subsequent `materialise` (`install.cpp:42`) unlinks them. A recoverable corrupt file is converted into permanent state loss with only a WARN.

**Evidence.** `src/env/manifest.cpp:123-166` (`json::parse` first statement in the try at `:124`; catch at `:162-164` WARN-only; `return m` at `:166` where `m` is empty from `:116`); file-absent handled at `:118-120` (no absent-vs-corrupt distinction — `json::parse` builds `j` fully or throws, so `m` is provably empty on the exception path). `src/env/manifest_impl.h:67-73` (read-modify-write under lock, no guard refusing to write after a failed read). `write_manifest` `manifest.cpp:169-203` (unconditional temp-then-rename overwrite). Trigger via `install.cpp:24-36` then `materialise` at `:42`. Other `with_manifest` callers: `cli.cpp:296,800,999`; `install.cpp:51,125`. The current atomic write only prevents corruption from den's own in-flight writes, not from these other sources.

**Fix sketch.** In `read_manifest`, distinguish "file absent" (return empty) from "file present but unparseable". On parse failure of an existing file, throw (or return a sentinel that `with_manifest` refuses to overwrite), so a corrupt manifest aborts the mutation instead of being silently clobbered. Optionally back up the corrupt file first.

**Verification step.** Add a test: seed `manifest.json` with two packages, corrupt it (truncate mid-JSON), run an install of a third package, and assert the command aborts (or refuses to write) and the two original packages are not lost. Separately assert an absent manifest still yields a clean empty manifest without error.

## Proposed bullseye targets (NOT filed)

The following are proposed under umbrella **"T5.x den Fable audit"**. They are recorded here only — no targets were created, no commit made, no PR opened.

- **T5.1** — `den install -s <name>` validates the package name with `is_valid_package_name` before any store-path or shell use, and `extract_build_recipe` invokes `brew info` via argv (no `/bin/sh -c`); a metacharacter name is rejected and executes nothing. (from F1)
- **T5.2** — `extract_archive` confines all writes to dest for symlink entries: symlink targets that are absolute or contain `..` are rejected (or SECURE_SYMLINKS is enabled); a crafted symlink-escape bottle writes nothing outside dest. (from F2)
- **T5.3** — `env_slug` produces a slug that can never act as a filesystem navigation component (`.`/`..` encoded or rejected); `den env remove ..` and `den env create /..` cannot escape `den_home/{manifests,envs}`. (from F3)
- **T5.4** — self-update refuses to replace the running binary unless a valid SHA256 checksum was fetched and matched; a release lacking a `.sha256` asset (or with an empty checksum body) aborts rather than overwriting. (from F4)
- **T5.5** — `read_manifest` distinguishes absent from corrupt; a present-but-unparseable `manifest.json` aborts the mutation (no clobber) instead of returning an empty manifest that the next write truncates. (from F5)
