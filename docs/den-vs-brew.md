# den vs Homebrew — capability matrix

This is the v1.0 feature-completeness artifact for den (🎯T74). Every row
states what Homebrew does, what den does, and a status:

- ✅ **parity** — den matches Homebrew on this capability.
- ⭐ **better** — den exceeds Homebrew (faster, safer, or more general).
- ⏳ **partial** — den ships a working subset; the remaining gap is tracked
  by an explicit follow-up target and is **post-v1**.

den consumes the Homebrew ecosystem directly — same Cellar
(`/opt/homebrew/Cellar`), same formulae, casks, taps, and bottles — so
"parity" usually means *literally the same artifacts*. Den rewrites the
bottles' Homebrew placeholders on pour: on macOS, Mach-O references go
through `<prefix>/opt/<dep>` where den owns that link and are pinned to
exact dependency kegs where it does not (always, in a prefix shared with
Homebrew; `den doctor` lists the pins in a private prefix); on Linux, ELF paths are patched with
patchelf. Den writes a prefix `opt/<name>` link only for a keg it poured
itself (when the link is missing or dangling, or moving its own link to a
newer keg), and never repoints an `opt/` link that points at a keg Homebrew
installed. Where den is marked ⭐, the win comes from its
independent store, environment model, multi-provider seam, or SAT solver.

## Matrix

| Capability | Homebrew | den | Status |
|---|---|---|---|
| **Install (bottle)** | `brew install jq` pours a prebuilt bottle into the Cellar and links into the prefix. | `den install jq` pours the same bottle into the shared Cellar (placeholders rewritten on pour; macOS deps bound through den-owned `opt/<dep>` links, pinned to exact kegs in a shared prefix; `opt/<name>` written only for den's own kegs, never repointed away from Homebrew's — #64) and links it into the active environment. | ⭐ better — ~23× faster install on M4 Max (🎯T68); per-environment linking instead of one global prefix. |
| **Linking into the prefix** | `brew link` symlinks each keg's `bin`, `sbin`, `lib`, `include`, `share`, `etc`, `var`, `Frameworks` into the prefix; conflicting files block the link unless `--overwrite`. | The root environment is linked into the prefix the same way (same dir set, brew-style relative links, shared dirs split into per-file links). A link into a den-managed keg is replaced; any other link or file blocks that package with a list of the conflicting paths, and `den install --overwrite <pkg>` replaces them. Unlink removes only links den recorded; existing `etc`/`var` config files are kept. `envs/ROOT` is a compat shim of links to the prefix dirs; `den update` migrates older installs. Named environments still link into `~/.den/envs/<name>`. | ✅ parity — prefix-relative tools (`aclocal --print-ac-dir`, `locate`) see every installed package. |
| **Post-install steps** | On install and upgrade `brew` runs `post_install`; for formulae with declarative `post_install_steps` in the formula API it applies those steps instead of evaluating Ruby (e.g. `openssl@3` symlinks `etc/openssl@3/cert.pem` → `etc/ca-certificates/cert.pem`; `ca-certificates` `run`s its `libexec/post-install` script to build that bundle). | den runs the `symlink` steps itself, natively, and executes no formula code (🎯T27): when a package is linked, each link is created as an absolute symlink, the way brew writes it. A `force` step replaces an existing file or link only on install, upgrade or `den use`; on any other materialise den only recreates a missing link. A step is applied only when its link lands under `<prefix>/etc` or `<prefix>/var` and its source is inside the prefix. Den never replaces a directory and never writes through a symlinked parent directory. A formula with any other step (`run`, `mkdir`, `glob`, conditions, …) has none of its steps applied, with a warning. Links are left in place on uninstall, as with brew. `ca-certificates`' `run` step is replaced by a native one: den copies the keg's `share/ca-certificates/cacert.pem` to `<prefix>/etc/ca-certificates/cert.pem` as a real file (temp file, then rename), on every install or upgrade of `ca-certificates`, and recreates it if it goes missing; it never writes it through a symlinked directory. `den doctor` warns when an `etc/*/cert.pem` link dangles. | ⏳ partial — gaps: on macOS brew's ca-certificates step also adds the certificates trusted in the system keychain to the bundle; den's bundle is the Mozilla bundle alone, so a certificate trusted only in the keychain (a corporate root, for example) is not trusted by den's openssl or curl. Other `run` steps are not executed, and Ruby `post_install` blocks without declarative steps are not run either. |
| **Source build** | `brew install --build-from-source` evaluates the Ruby formula and compiles. | `den install -s/--build-from-source` builds via the bundled Ruby (complex formulae) or the native C++ fast-path parser (simple ones), with a shim-free macOS toolchain (`SDKROOT`/`-isysroot`, `/usr/bin/ld`, no `xcrun`). | ✅ parity — works today. Native-parser coverage is still narrower than Ruby (dependency extraction 🎯T58, no-Ruby SIMPLE installs 🎯T59); Ruby remains the complex-formula path, so no functional gap. |
| **Uninstall / cleanup** | `brew uninstall <f>` refuses while installed formulae depend on `<f>` at runtime (listing them; `--ignore-dependencies` overrides), then deletes the keg, unlinks it from the prefix and removes its `opt/` link; by default it then autoremoves dependencies nothing else needs (unless `HOMEBREW_NO_AUTOREMOVE`). `brew cleanup` prunes old versions and the download cache. | `den uninstall <pkg>` likewise refuses, listing each dependent and its environment and exiting non-zero, while an installed Homebrew package in any environment needs `<pkg>` at runtime (transitively; build-only dependencies don't count; a dependent whose environment still gets `<pkg>` from its own manifest or another ancestor doesn't block). `--ignore-dependencies` overrides. Otherwise it drops the package (and its pin) from the active environment and re-materialises it. The keg stays on disk for a fast reinstall; if no environment still uses that version, den hands `opt/<name>` to another installed version den manages and an environment still uses, or removes the link. `opt/` links to Homebrew's kegs are never touched. `den cleanup` deletes den-owned kegs no environment references, with their `opt/` links, and clears the archive cache. | ⏳ partial — gap: `den uninstall` does not autoremove the auto-installed dependencies it leaves behind; they stay in the manifest until `den autoremove` is run by hand. |
| **Third-party taps** | `brew tap user/repo`; tapped formulae resolve and install. | `den tap add user/repo [source]`, `den tap --list`, `den tap --remove`; tapped formulae merge into the index and install via the source-build path (🎯T67). | ✅ parity |
| **Casks** | `brew install --cask` installs macOS apps (DMG/ZIP/PKG, scripts, uninstall/zap stanzas). | `den install <cask>` (no `--cask` flag) installs DMG, ZIP/tarball, `.app` and binary-only casks on macOS: the archive is staged under `~/.den/caskroom/<token>/<version>/` (never Homebrew's Caskroom), the new app is staged beside the target in `DEN_APPDIR` (default `/Applications`) and swapped in only once fully staged, with rollback to the old version on any failure (#61, #62). Den writes `DEN_CASK_RECEIPT.json` and only overwrites or removes apps its own receipt names. `.pkg` casks run `installer`. Casks are excluded from daemon auto-upgrade (#66) and are unsupported on Linux. | ⏳ partial (🎯T12) — not yet handled: `.pkg` installs need admin (den runs `installer` without elevation) and uninstall does not run `pkgutil --forget`; `preflight`/`postflight` and installer scripts; `uninstall` stanzas (launchctl, quit, signal, delete…); `zap`; and quitting a running app before uninstall/upgrade. |
| **Multi-version coinstall** | Versioned formulae (`python@3.11`, `python@3.12`) coexist; switching is manual relinking. | Installing a new version never removes the old one; `den use <name> <version>` atomically switches which version the active environment links. | ⭐ better — multi-version is the default, switch is one atomic command per environment, rollback is instant. |
| **Dependency resolution** | Greedy dependency walk; conflicts surface as install failures. | CDCL/DPLL SAT solver with stability-biased preferences and multi-version awareness; `den deps --explain` prints the clauses, preferences, and conflicts behind an assignment. | ⭐ better — complete solver with explainable UNSAT, replaces the prior greedy DFS. |
| **Environments / isolation** | One global prefix; no first-class isolated environments. | Named environments are symlink sets under `~/.den/envs/`; they compose via PATH precedence (a project env overrides the default). `den env create/list/use/remove/show/freeze`. | ⭐ better — virtualenv-style isolation for *every* package, not just Python; `env freeze` exports a lockfile. |
| **Python packages** | Not a Homebrew concern (formulae only). | `den install --provider pip <pkg>`; uniform `list`/`info`/`uninstall`/`run` through the `pip` provider (🎯T60). | ⭐ better — single tool spans Homebrew + pip. |
| **Node packages** | Not a Homebrew concern. | `den install --provider npm <pkg>` via the `npm` provider (🎯T60). | ⭐ better |
| **Go packages** | Not a Homebrew concern. | `den install --provider go <pkg>` via the `go` provider (`go install`) (🎯T60). | ⏳ partial — curated bare aliases (e.g. `staticcheck`, `gofumpt`) install end-to-end; full module paths (`host/path@version`) are rejected/mis-materialised. Tracked: 🎯T77. |
| **Cargo packages** | Not a Homebrew concern. | `den install --provider cargo <pkg>` via the `cargo` provider (`cargo install`) (🎯T60). | ⭐ better |
| **Search** | `brew search` substring match on names/descriptions. | `den search` case-insensitive substring match on name + description over the local index. | ⏳ partial — keyword parity today. Semantic (embedding/LLM) search is post-v1: 🎯T62 (relevance), 🎯T24 (provider hierarchy), 🎯T25 (corpus CI pipeline). |
| **Services** | `brew services start/stop/...` via launchd/systemd. | `den services list/start/stop/restart/status/logs` with a built-in supervisor (no launchctl); dependency-ordered stop and restart. | ⏳ partial — built-in supervisor manages services today; full launchctl-free supervisor hardening is 🎯T61. Restart-after-upgrade is 🎯T52. |
| **Upgrades** | `brew upgrade [pkg]`; in-place, foreground; an in-use binary can break. | `den upgrade [pkg]` per-provider; a background daemon stages upgrades alongside existing versions without touching the active env. Installed dependents that homebrew-core revision-bumped for the new version (same upstream version, higher `_<revision>`) are upgraded in the same batch, as `brew upgrade` does; pinned ones are reported and left. A package that cannot be linked is rolled back with the dependents it brought in, and every `<prefix>/opt/<dep>` link the batch moved forward is pointed back unless a change that stayed applied needs it. | ⭐ better — ~6× faster on the upgrade path (🎯T68); staged, non-destructive, instant rollback. |
| **Upgrade: defer-while-in-use** | No deferral; upgrading a running tool can clobber it. | The daemon detects in-use keg files (`lsof` / `/proc`) and defers the upgrade; deferred items surface in `den outdated` and `den daemon status` with a reason (🎯T72). | ⭐ better — no Homebrew equivalent. |
| **Disabled packages** | `brew install`/`brew upgrade` refuse a formula homebrew-core has `disable!`d, including a dependency it would fetch or install ("has been disabled because it ..."); a disabled dependency already installed is skipped silently. `--force` turns the refusal into a warning for formulae; a disabled cask cannot be installed at all. | `den install` and `den upgrade` refuse a named formula or cask the index marks disabled, a package whose install or new version would pour a disabled dependency ("error: 'foo' needs 'bar', which is disabled upstream: it ... (disabled on <date>; replacement: <name>)"), and a revision-bumped dependent that is disabled; the other names proceed and the run exits 1. A disabled dependency already installed at the index version is not mentioned; one already up to date when named is a warning. `--force` installs or upgrades disabled formulae with the message as a warning; disabled casks are refused regardless. `den install -s` applies the same checks to every dependency it would pour or build, build-only ones included. A bare `den upgrade` still leaves disabled formulae out. The daemon's auto-upgrade applies the same check with no bypass: an upgrade that would pour a disabled package (itself, a new dependency, or a revision-bumped dependent, whose refusal holds the whole batch) is skipped, logged, recorded in the daemon state with every disabled package in the way and the time it was found, and listed with that time by `den status`, `den outdated`, `den daemon status` and `den doctor` until it applies or is no longer pending. | ✅ parity |
| **Pinning** | `brew pin <f>` holds a formula at its installed version; `brew upgrade` skips it (and errors when named explicitly); `brew list --pinned`; `brew unpin`. Uninstall drops the pin. | `den pin <pkg>...` pins at the active version, `den pin`/`den pin --list` lists pins (flagging ones no longer installed or switched with `den use`), `den unpin <pkg>...`. `den upgrade` skips pinned packages ("Not upgrading N pinned package(s)") and refuses a pinned name with a non-zero exit; the daemon never pre-downloads a pinned package's bottle and its auto-upgrade pass never applies a pinned upgrade (it stays visible in `den outdated`, tagged `[pinned at V]`). Uninstall drops the pin. A corrupt `~/.den/pins.json` fails closed (holds every upgrade and skips every daemon pre-download). | ✅ parity — pins are global to den_home (not per environment); `den use` can still switch a pinned package manually. |
| **Downgrades** | `brew upgrade` orders a formula against the installed keg by `(version_scheme, version, revision)`: a homebrew-core move to a lower version with a `version_scheme` bump (e.g. `openssl@3` 3.6.x → 3.5.9 LTS, scheme 1) is an upgrade; a lower version in the same scheme is not. | `den upgrade` and the daemon's auto-upgrade use the same `(version_scheme, version, revision)` ordering (so `3.6.3_1` > `3.6.3`, and a scheme bump to a higher version is an upgrade), with one rule on top: an upgrade never lowers the version. The installed side's scheme comes from the keg's `DEN_RECEIPT.json`, else Homebrew's `INSTALL_RECEIPT.json` (`source.versions.version_scheme`), else 0; the index side's from the formula's `version_scheme`. A lower version with a higher scheme (`openssl@3` 3.6.3 → 3.5.9, scheme 1) is held and reported with its reason ("held: index pins 3.5.9 (version_scheme 1), below installed 3.6.3"); a lower tuple (an index that lags what is installed) is skipped and reported as "index older than installed". Both show in `den upgrade` (and `den upgrade --dry-run`), `den outdated`, `den status`, `den daemon status` and `daemon.log`, and neither is ever applied. Downgrading takes an explicit `den use <pkg> <version>`. | ⚠️ deliberately stricter than brew: a scheme bump to a lower version is held, not applied; plus an explicit report instead of a silent skip. |
| **Migration from brew** | n/a (Homebrew is the source). | `den migrate` records formulae in the root environment manifest (`manifests/ROOT/manifest.json`, the file `den list` reads), and records casks, taps, and brew services in den's settings and service store. Non-destructive (Cellar byte-identical), idempotent, merges with packages already in the root manifest, with a post-migration health check, `--dry-run`, and opt-in `--integrate-shell` (🎯T71). | ⭐ better — one-shot, reversible adoption; `brew` keeps working afterward. |
| **Trust / verification** | Bottle SHA256 checked against the same Homebrew API that served it (single source of truth). | Install-time cross-check of the Homebrew API hash against den's replica snapshot (`data/known_hashes.json`), read **locally** from the copy shipped with den (or a `~/.den/trust/known_hashes.json` override) — no network fetch from `raw.githubusercontent.com` or anywhere else happens at install time. A mismatch refuses; a corrupt snapshot refuses (fails closed); a bottle with no replica entry, or no snapshot at all, installs on the Homebrew hash alone with a warning and is counted as a degraded install in `den doctor` and `den daemon status`. Caveat: replica entries are seeded by CI (`replica-verify.yml`, `den replica-verify`, 🎯T64) from formulae.brew.sh's own hashes, each confirmed by pulling that bottle from GHCR — so the replica is an earlier, GHCR-confirmed copy of Homebrew's hash, not an independent root: it catches the API changing a hash after the snapshot was taken, not a bottle that was already bad when it was seeded. | ⭐ better — detects a later swap of a covered bottle's hash, which brew alone cannot; coverage is limited to bottles in the snapshot. Advanced layers (sigstore/transparency-log style) are post-v1: 🎯T44. |
| **Host introspection** | `brew config` / `brew doctor` report toolchain and environment. | `den config` / `den doctor` report Xcode / CLT / SDK (host facts on Linux) plus `brew config` parity keys (🎯T66). | ✅ parity (superset of `brew config` keys) |
| **Cellar introspection** | `brew list`, `brew --cellar`; no per-keg disk/ref view. | `den list --cellar` shows per-keg disk usage, environment references, and orphans; `den whence` maps a file/command to its owning keg (🎯T66). | ⭐ better — orphan and reference reporting Homebrew lacks. |
| **Performance** | Ruby startup tax on every invocation. | Native C++ binary; benchmarked against `brew` on the same hardware (`scripts/bench/`, `bench.yml` CI). | ⭐ better — ~6× on list/info/search/upgrade, ~23× on install (M4 Max, 🎯T68). |

## Post-v1 gaps (tracked, not shipped)

These are deliberately out of scope for v1.0 and each has a convergence
target:

| Area | Target(s) | Why deferred |
|---|---|---|
| Semantic search (embedding + LLM) | 🎯T62, 🎯T24, 🎯T25 | Keyword search covers the v1 need; semantic search needs a pre-baked corpus index and a CI pipeline. |
| Content-addressed Cellar + explicit bindings | 🎯T69, 🎯T26, 🎯T28 | The shared-Cellar model ships v1; content-addressing is a storage-layer evolution that must land without regression. |
| Opt-in telemetry | 🎯T70, 🎯T32 | Privacy-first; only ships once reports are transparent and actionable. |
| Built-in supervisor hardening | 🎯T61 | Services work today; full launchctl-free supervisor parity is incremental. |
| Advanced trust layers | 🎯T44 | The replica cross-check ships v1; transparency-log / signature layering is additive. |
| Restart services after upgrade | 🎯T52 | Deferred-upgrade detection ships v1 (🎯T72); auto-restart orchestration follows. |
| Native parser → Ruby-free SIMPLE installs | 🎯T58, 🎯T59 | Ruby remains the complex-formula path; the native fast-path widens over time. |

No row above is a regression against Homebrew: every line is parity or
better, and every ⏳ row ships a working subset with the remainder tracked.
